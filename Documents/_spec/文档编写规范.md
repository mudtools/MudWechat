# API SDK 文档编写规范 v1

> 项目无关的文档编写规范。适用于任何「以声明式接口暴露大量远程 API 端点」的 SDK 仓库。
> 本规范只定义**结构与取证纪律**，不复述任何具体项目的接口明细——明细永远在源码与契约守卫里。

适用范围：`Documents/` 下全部项目文档。新增项目、新增产品线、新增业务域，都按本规范落位，不另立规则。

---

## 1 三条基本判断

先说清楚规范为什么长成这样，后面所有细则都是这三条的推论。

**① 文档的读者是「要调这个接口的人」，不是「想了解 SDK 架构的人」。**
判定标准只有一个：读者读完这一篇，能不能在自己的工程里把这次调用写对。架构动机、实现取舍、内部治理属于仓库内的域 README 和设计方案文档，不进 `reference/`。同一份事实可以在两处出现，但视角必须不同——域 README 写「本域契约是什么、为什么这样切」，`reference/` 写「你怎么用、会踩什么」。

**② 代码与契约守卫是唯一事实来源，文档是它们下游的解释层。**
文档里任何一句关于路由、字段名、令牌、必填性、端点计数的断言，都必须能指到接口声明、DTO 或守卫断言。指不到的，要么去官方页取证后标明出处，要么写进「已知留档缺口」标为未核验。**不允许用「通常」「一般」「应该」填空**——这是批量写上千篇文档时唯一不会腐烂的纪律。

**③ 文档粒度按「接口族」而非「端点」切，是为了让文件数与检索性同时成立。**
一个 SDK 的端点数量在数百到上千。一端点一篇会把目录变成检索灾难，且无法表达端点之间的对比关系（同一业务动作的多种令牌/场景变体，恰恰是最容易写错的地方）；一域一篇则单文件过长、diff 噪音大。一接口族一篇、端点作小节，族内对比可以放在同一张表里，文件数落在「族数」量级。

## 2 目录规划

```
Documents/
  README.md                    # 多项目入口：项目索引 + 规范索引
  _spec/
    文档编写规范.md             # 本文件（项目无关，唯一规范）
    模板/
      接口族文档.md             # L3 骨架，复制后填空
  <项目名>/                     # 一个项目一层，项目名用仓库名（ASCII，与代码仓一致）
    README.md                  # 项目文档索引 + 覆盖进度表
    guide/                     # 接入指南：跨端点、按任务组织，人工撰写
    reference/                 # 接口参考：与源码目录逐段映射（本规范主体）
      <线或模块>/<域>/<接口族>.md
    appendix/                  # 附录：错误码、术语、频率上限等横切事实
```

### 2.1 路径 ⇔ 源码映射（硬约束）

`reference/` 下的相对路径必须与源码中该接口族目录的**相对路径逐段一致**，段名照抄源码目录名（ASCII、PascalCase），不做翻译、不改大小写、不加编号前缀。

| 项目形态 | 源码目录 | 文档路径 |
|---|---|---|
| 多产品线共仓（如 Mud.Wechat） | `Src/<线>/<主包>/Interfaces/<域>/<族>/` | `reference/<线>/<域>/<族>.md` |
| 单产品线 | `<主包>/Apis/<域>/` | `reference/<域>/<族>.md` |

规则写死的收益：① 任何人都能从文档反查源码、从源码定位文档；② 覆盖度可以脚本核对（每个接口族目录是否有对应 `.md`），不需要人工维护清单；③ 源码目录改名时，漏改的文档路径会立刻在链接检查里暴露。

代价与约束：中文不进路径。标题、正文、表头用中文；文件与目录名一律 ASCII 段名。这同时避开了 Windows 工具链的编码与 `MAX_PATH` 问题（含 BOM 的脚本、PowerShell 5.1 递归枚举），不要把文档路径做成构建门禁的负担。

### 2.2 深度与文件名长度

目录深度封顶 4 层（`Documents/<项目>/reference/<线>/<域>/<族>.md`）。族名过长时（超过 40 字符）用源码里该族的**短名段**而不是自行缩写——缩写会让人放弃核对映射。

### 2.3 什么进 `guide/`，什么进 `reference/`

| 内容 | 归属 |
|---|---|
| 装包、配凭据、跑通第一次调用 | `guide/快速开始.md` |
| 应用类型/租户/令牌模型、多应用切换 | `guide/配置与凭据.md` |
| 判错、重试、限流退避的通用契约 | `guide/错误处理.md` |
| 某个接口族怎么调 | `reference/.../<族>.md` |
| 全局错误码、频率上限、术语 | `appendix/` |

`guide/` 不复述端点参数表，`reference/` 不讲 SDK 安装。两边都写=两处漂移的起点。

### 2.4 单文件端点上限

一篇接口族文档的端点小节上限 **20**。超过则按业务子族拆分（拆批依据写进族文档首屏的「本族文档切分」说明），并在 `reference/` 的项目索引里登记拆分关系。**不得**为省事把 30 个端点塞进一篇——超长文件在评审和 diff 上都不可读，等于没写。

## 3 分层与每层职责

| 层 | 文件 | 该写 | 不该写 |
|---|---|---|---|
| L0 | `Documents/README.md` | 有哪些项目、规范在哪 | 任何接口内容 |
| L1 | `Documents/<项目>/README.md` | 产品线/模块地图、覆盖进度表、从哪读起 | 端点明细 |
| L2 | `reference/<线>/README.md`（可选） | 线内业务域清单、跨域共性（令牌模型、注册入口形态） | 参数表 |
| L3 | `reference/<线>/<域>/<族>.md` | **端点的完整调用契约**（本规范的核心交付） | SDK 安装、架构动机 |
| L4 | 域内总览（可由源码目录 README 承担） | 族清单、端点速览表、契约陷阱汇总 | 单端点参数表复述 |

L2/L4 是否成文由项目现状决定：**已有域 README 的项目不要重抄一份**，L3 文档直接相对链接过去。文档体系的价值在 L3，其余层是索引。

## 4 L3 单篇结构

固定骨架、固定顺序。缺项写「无」或删除并在文末说明，不得静默省略。骨架见 [`模板/接口族文档.md`](./模板/接口族文档.md)。

| # | 小节 | 必填 | 内容纪律 |
|---|---|---|---|
| 0 | 文档元信息 | 是 | 表格：所属产品线 / NuGet 包与版本 / 接口与 DTO 源文件 / 契约守卫 / 官方文档号与页面更新日期 / 状态 / 本文核验日期 / 示例代码验证方式 / 证据基础 |
| 1 | 这个接口族做什么 | 是 | 3–6 句说清业务动作与**使用时机**；一句话给「不该用本族」的反例 |
| 2 | 前置条件 | 是 | 凭据配置项（属性名 + 校验时机）+ 权限/可见范围要求 + 官方开放的应用类型。**不得**出现真实密钥值 |
| 3 | 接口族与注册 | 是 | 族内接口清单表（父/子接口、命名空间、可否 DI 注入、端点数、端点编号索引）+ DI 注册入口一行 |
| 4..N | 端点小节 | 是 | 每端点固定子结构：签名 → HTTP 与凭据 → 请求参数表 → 请求示例 → 响应参数表 → 返回示例 → 调用示例 → 本端点注意事项。见 §4.1 |
| N+1 | 陷阱与易混对照 | 是 | 至少一条；确实没有则写「本族无已知反直觉点，末次核查 <日期>」 |
| N+2 | 失败处理与错误码 | 是 | 只写本文可核验的码，其余指向 `appendix/` |
| N+3 | 已知留档缺口 | 条件 | 凡在 §5 三类证据内核验不到的项，逐条列出并标 **未逐项核验** |
| N+4 | 延伸阅读 | 是 | 相对链接：同域兄弟族、邻域、`guide/` 对应篇 |

### 4.1 参数表写法（最容易腐烂的地方）

请求参数表固定列：

```
| 参数 | JSON 字段名 | 类型（C#） | 必填 | 说明与限制 |
```

- **「参数」列写 SDK 侧的名字**（C# 属性/方法参数），「JSON 字段名」列照抄官方原文拼写。两列不一致是本仓最常见的踩坑点（官方裸值跨域同名、`_list` 后缀时有时无），必须显式暴露而不是合并。
- **类型写 C# 声明类型**，含可空性（`List<string>?`）。可空性与「官方必填」是两个正交事实：DTO 因 AOT/配置绑定形态统一用可空属性，官方仍可能必填——两列都要写，谁也不能替谁推断。
- **必填性只写官方口径**（是/否），并注明 SDK 不做参数校验（声明式客户端把非法值原样交给官方，错误以 `errcode` 回来）。
- **数值限制照抄**（`≤1000`、`1800s`、`最多一次`）并标出处：来自接口 XML 注释、DTO 注释，还是官方页。
- 官方有「同一文档页覆盖多个场景、字段随场景变化」的情况，用**场景对照表**而不是混在一张参数表里。

响应参数表固定列：`| 字段（JSON） | 属性（C#） | 类型 | 说明 |`。

### 4.2 代码示例纪律

1. **可编译**。示例不是伪代码：命名空间、扩展方法签名、属性名都要对着真实声明写过。无法确认的写法宁可不写。
2. **最小完整链路**：注册凭据 → 注册模块 → 解析服务 → 调用 → **判错** → 取业务字段。省略任何一环都会被读者照抄成缺陷。
3. **示例必须自足**。除宿主约定标识符（`builder` / `config` / `provider` / `logger` / `cancellationToken`，且要在注释里点明它们由谁提供）之外，示例引用的每个名字都必须在示例内显式声明。业务输入也要在示例里落声明（`var encryptedUserIds = new List<string>();`），不能留成自由变量——「读者复制即编译不过」是最常见的文档缺陷，且只有把 using 块一起收窄着编译才会暴露。
4. **判错必须出现**。这是 SDK 侧最容易出错的一点，规范层面强制：声明式客户端**不替调用方判错**，官方 `errcode != 0` 时 HTTP 仍是 200、响应照样反序列化成功。示例必须演示 `IsSuccess` / `ErrorCode` 分支，或显式调用 SDK 的判错出口（如 `WechatWorkException.ThrowIfFailed`）。
5. **凭据零真实值**。用占位符或环境变量读取，并在示例注释里点明凭据来源约定。绝不写 `corpsecret`、`provider_secret`、`permanent_code` 的真实形态示例值。
6. **注释只写坑**，不写「这行调用某某接口」这类与代码同义的废话。
7. 每篇文档最多 1 个完整示例 + 若干片段。多应用/多租户切换若与本族相关，写成「本族令牌为服务商级，无需企业作用域切换」，而不是把整套作用域 API 搬进来。

**编译验证的做法**（不是可选项，`已核验` 状态的前提）：在仓库的 gitignored 临时目录建一个单 TFM 验证工程，引用被测包，把文档里的示例**逐字**贴进去编译，验完即删。两条注意：① 若仓库根 `Directory.Build.props` 施加多 TFM/AOT 治理，验证工程需要一层目录级 props 遮蔽根继承，否则会因 `TargetFrameworks` 与 `OutputType=Exe` 冲突直接建不起来；② 贴进去的 using 块要**只保留文档里写的那几行**，多一个都别加——命名空间缺失（典型如扩展方法所在的 `Abstractions` 面）恰恰只有在这种严格条件下才会暴露，宽容的 using 列表等于把缺陷留给读者。宿主隐式 using 覆盖的命名空间不必写进文档，但要在示例注释里点明「由 SDK 隐式提供」，否则换宿主形态（如非 Web 的控制台）就会编译不过。

### 4.3 令牌与凭据小节怎么写

SDK 的凭据面是读者最没有安全感的地方，每篇 L3 的「前置条件」必须回答四件事，缺一件就会被问到工单里：

| 问题 | 口径 |
|---|---|
| 用哪个凭据 | 写凭据的**官方参数名**（`provider_access_token`）+ SDK 令牌类型常量（`WechatTokenTypes.ProviderAccessToken`）+ 注册表键（如 `Wechat.AccessToken@Corp`） |
| 谁负责取 | 明确「SDK 自动换取并缓存/刷新，开发者不接触凭据」还是「宿主必须显式传入」；后者要在示例里出现该参数 |
| 会不会出现在 URL | 注入方式（Query / Header）+ 是否已在日志脱敏词表内 + 是否有已接受风险编号（如 MUD005「官方契约强制 Query，无法改 Header」） |
| 拿错了会怎样 | 有没有归属校验、失败形态是异常还是静默取错值。fail-fast 的要点名异常类型 |

## 5 取证纪律（写之前必须做，写之后必须留痕）

**三类内部证据**（优先级从高到低）：

1. **契约守卫**（`Tests/**/ContractGuards/`）——路由、端点计数、令牌绑定、字段名的权威描述。
2. **接口与 DTO 的 XML 文档注释**——官方文档号、业务限制（频率、批量上限、覆盖删除、权限可见范围）的落点。
3. **域 README / 设计方案**——族切分动机、已知陷阱汇总，用于交叉印证，不作为路由依据。

**一类外部证据**：官方文档页。需要官方页时按以下纪律，否则宁可不写：

- 正文由 JS 渲染的站点**必须渲染后取**（直接抓 HTML 常只拿到导航，据此写成空断言比不写更糟）。
- 记下**页面标注的「最后更新」日期**与**本文核验日期**，两者都要出现在元信息表。官方页会改版，只留一个日期的文档无法判断腐坏程度。
- 同一动作对多种应用类型有独立页面（第三方 / 代开发 / 自建）时，逐页取；**若某应用类型官方无页面，那是「官方未开放」的证据**，写成零端点/无子接口的断言，不要按其他类型推断字段。
- 官方页与代码断言冲突时，**以代码为准，并同批提出代码/守卫的修订**，不在文档里写「可能」两头讨好。文档没有纠正契约的权限，只有暴露矛盾的职责。

**未核验项的处置**：核验不到就单列「已知留档缺口」，写清楚缺什么、为什么缺、需要时去查哪里（邻域守卫 / 邻域方案），并标 **未逐项核验**。这是本仓既有的成熟做法，直接沿用。把未核验项写成推断，是批量文档化最危险的失败模式——错误会被复制上千次。

## 6 排版与措辞

- 中文正文，全角标点；英文/数字与中文之间不加空格也不刻意删除，保持与既有仓库文档一致。
- 代码标识符一律反引号包裹：`GetUserAsync`、`access_token`、`WechatModule.AccountId`。文件名、路由、参数名同理。
- 标题层级：文档主标题 `#`，一级小节 `##`，端点小节 `###`，端点内子块 `####`。元信息表在主标题下方、第一个 `##` 之前。
- 表格前列固定顺序，不要在篇与篇之间换列顺序——读者用列位定位信息，不是用列名。
- 端点小节标题格式：`### <编号>. <方法名> — <一句话动作>`，编号用族内序号（`E1`、`E2`…），供跨文档引用「见 AccountId/Bot#E1」。
- 强调只用于**读者会因此写出缺陷**的词（如「仅代开发开放」「不可回退」「同路由多方法」），一段里最多一处。满屏加粗等于没有加粗。
- 不使用 emoji、不使用感叹号式提醒、不写「注意！」单独成段——注意事项写进注意事项的条目里，靠内容而非语气生效。
- 术语首次出现给定义或链接，此后不重复解释。跨项目共用术语进 `appendix/术语表.md`。
- 相对链接必须可解析；从 `reference/` 指向源码用相对路径，指向官方页用完整 URL 并在同处标官方文档号。

## 7 状态标记与覆盖进度

元信息表「状态」列取值三个，别的都不合法：

| 状态 | 含义 |
|---|---|
| `草稿` | 结构填完，未经第二人评审或未做官方取证 |
| `已核验` | 正文每个断言可指到内部三类证据或带日期官方取文 + 示例逐字编译通过 + §7 只登记「官方未提供」或「本文不主张」的项（缺口表存在本身不降级，它正是诚实的体现） |
| `待补充` | 正文自身有未闭合项：某字段的必填性/口径在证据里无法定论、某端点参数表还没写完、依赖的 `guide/`·`appendix/` 篇目缺失到影响本篇可读 |

`已核验` 是唯一可对外引用的状态。升到这个状态需要三件事同时成立：**每个断言都能指到内部三类证据或带日期的官方取文**、**示例代码逐字编译通过**、**元信息表的「证据基础」行写清哪部分是本次官方取文、哪部分是继承本域带日期的核验留档**。三者缺一，停在 `草稿`。

**不要求每篇都重新取官方页**：已被守卫与注释钉住的事实重复取文只增加限流风险、不增加证据强度。但凡某事实**只有官方页能支撑**（频率数值、错误码、必填性而内部证据未记），必须本次取文并记日期，否则不得写入正文，只能进「已知留档缺口」。

**编译级 ≠ 运行级**：`示例代码验证` 一行只声明「逐字编译通过」。运行级验证需要真实凭据与真账号，不在文档验收范围内；已做过运行验证的在证据基础行单列注明，未做过的**不得**用「已验证可用」这类措辞。

项目索引 `Documents/<项目>/README.md` 维护覆盖进度表：按产品线/模块列「域数 / 族数 / 已成文 / 已核验」，未成文的域按源码目录倒推缺口，不靠人工记忆。

## 8 维护纪律

- **同批修改**：接口/DTO/路由/令牌/注册入口任一变更，对应 L3 文档必须同批改，与「改契约面必同批改守卫」是同一条纪律。评审时文档与守卫的改动应出现在同一个提交里，否则视为半成品。
- **核验日期重置**：改动端点参数表、令牌口径、错误码后，元信息表的核验日期必须重置为本次核验日期，不得沿用。
- **版本锚点**：元信息表里的 SDK 版本取仓库版本唯一来源（`Directory.Build.props` 的 `Version`），不写「最新版」。
- **文档改动不进 CHANGELOG**，CHANGELOG 只记面向消费者的行为变更；但「文档与契约漂移」算缺陷，按缺陷流程修。
- **删除即删除**：端点退役时同批删除对应小节；若整族退役，删文件并在域索引留一行退役说明（含退役版本），不要留「已废弃」空文件。
- **不为消警告/凑覆盖而写**：填充模板空壳比不写更糟——它让进度表说谎。

## 9 提交前自检（逐篇）

1. 元信息表逐项齐全（产品线 / 包与版本 / 源文件 / 守卫 / 官方号与页面更新日期 / 状态 / 核验日期 / 示例验证方式 / 证据基础）？
2. 「前置条件」能否让读者配出凭据？有没有真实密钥值？
3. 参数表：JSON 字段名与 SDK 属性名两列都写了吗？必填性与可空性分开写了吗？数值限制有出处吗？
4. 调用示例：在本仓里编译过吗（using 块严格按文档所写，不加宽）？含判错分支吗？凭据是占位符吗？
5. 「陷阱与易混对照」是否至少一条，且指的是**会导致调用失败或静默错结果**的点？
6. 错误码是否只写了本文可核验的、其余指向 `appendix/`？
7. 有没有任何一句断言指不到三类内部证据或带日期的官方取证？指不到的进了「已知留档缺口」？
8. 相对链接是否都可解析（含指向源码与 `guide/`）？
9. 文档路径与源码接口族目录是否逐段一致？
10. 契约面变更是否同批改了守卫？（本条与仓库 `AGENTS.md` §9 的门禁要求衔接）

## 10 反模式（见到即返工）

| 反模式 | 为什么禁 |
|---|---|
| 把官方页整段抄进文档 | 官方页会改版，抄来的就是定时炸弹；SDK 文档的价值在「SDK 侧怎么调」，不在复述上游契约 |
| 用「通常/一般/应该」描述字段必填性或路由 | 路由与必填性是确定事实，模糊措辞等于把核验成本转嫁给读者 |
| 示例代码里省略判错 | 声明式客户端不自动判错，省略即诱导读者写出「errcode 非 0 当成功」的缺陷 |
| 参数表只写 C# 属性名 | 官方字段名拼写反直觉（缺 `_list` 后缀、裸值同名跨族），抓包对不上时读者无从排查 |
| 一篇文档讲完整个 SDK 的多应用/令牌体系 | 与 `guide/` 重复，两处漂移；L3 只回答「本族用哪个凭据、谁负责取」 |
| 用架构动机解释端点存在性 | 读者要的是「我该调哪个」，动机放域 README；写进 L3 会让参数表沉到第三屏 |
| 进度表按「写过的文件数」统计 | 空壳文件会灌水，只统计升到 `已核验` 的篇数 |
| 一端点一篇 | 文件数上千，目录失去可浏览性，端点间对比关系散落各处 |
| 中文进文件/目录名 | 路径映射不可机器核对，且踩 Windows 工具链编码/长度问题 |
| 未核验项写成断言 | 批量场景下错误被复制上千次，是文档化项目唯一不可逆的失败 |
